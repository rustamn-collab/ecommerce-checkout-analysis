# 14. Безопасность

## 14.1. Назначение документа

Раздел описывает меры безопасности системы оформления заказа. Документ содержит:

- Модель угроз (Threat Model).
- Аутентификацию и авторизацию.
- Защиту данных (шифрование, токенизация).
- Соответствие PCI DSS.
- Соответствие 152-ФЗ.
- Защиту от атак (OWASP Top 10).
- Rate limiting и антифрод.
- Аудит и логирование.
- Управление секретами.
- Безопасность инфраструктуры.
- Инцидент-реагирование.

**Цель:** защитить данные клиентов, исключить утечки, обеспечить соответствие требованиям регуляторов.

## 14.2. Модель угроз (Threat Model)

### 14.2.1. Активы (что защищаем)

| Актив | Критичность |
|-------|-------------|
| Персональные данные клиентов | Высокая |
| Платёжные данные | Критическая |
| История заказов | Средняя |
| Сессии и токены | Высокая |
| Секреты и ключи | Критическая |
| Внутренние API | Высокая |
| База данных | Критическая |

### 14.2.2. Угрозы (STRIDE)

| Категория | Угроза | Пример | Митигация |
|-----------|--------|--------|-----------|
| **S**poofing | Подмена пользователя | Кража токена | JWT + короткий TTL + refresh |
| **T**ampering | Изменение данных | SQL-инъекция | Prepared statements |
| **R**epudiation | Отказ от действий | Клиент отрицает заказ | Аудит + логи |
| **I**nformation Disclosure | Утечка данных | Логи с ПДн | Маскирование, шифрование |
| **D**enial of Service | DoS-атака | 100k RPS | Rate limiting + WAF |
| **E**levation of Privilege | Повышение прав | IDOR | Проверка ownership |

### 14.2.3. Векторы атак

| Вектор | Описание | Митигация |
|--------|----------|-----------|
| Brute force | Подбор пароля | Rate limiting, CAPTCHA, MFA |
| Credential stuffing | Использование утёкших паролей | Проверка по базам утечек |
| SQL injection | Внедрение SQL-кода | Prepared statements, ORM |
| XSS | Внедрение JS | Экранирование, CSP |
| CSRF | Подделка запросов | CSRF-токены, SameSite cookies |
| MITM | Перехват трафика | TLS 1.3, HSTS |
| IDOR | Доступ к чужим объектам | Проверка ownership |
| SSRF | Запросы к внутренним сервисам | Whitelist URL |
| DDoS | Перегрузка | Cloudflare, WAF, autoscaling |
| Insider threat | Угроза изнутри | RBAC, аудит, least privilege |

## 14.3. Аутентификация

### 14.3.1. Схема

**JWT (JSON Web Token)** + **OAuth 2.0** для внешних клиентов.

```
Клиент → Auth Service → JWT (access + refresh)
Клиент → API Gateway (Bearer JWT) → Микросервисы
```

### 14.3.2. Структура JWT

**Header:**
```json
{
  "alg": "RS256",
  "typ": "JWT"
}
```

**Payload:**
```json
{
  "sub": "u1u2u3u4-v5v6-7w8x-9y0z-1a2b3c4d5e6f",
  "iss": "auth.example.com",
  "aud": "api.example.com",
  "exp": 1729084800,
  "iat": 1729081200,
  "roles": ["USER"],
  "jti": "j1j2j3j4"
}
```

**Signature:** RSA-256.

### 14.3.3. Параметры токенов

| Параметр | Access Token | Refresh Token |
|----------|--------------|---------------|
| TTL | 1 час | 30 дней |
| Алгоритм | RS256 | RS256 |
| Хранение | В памяти | HttpOnly cookie |
| Обновление | Через `/auth/refresh` | Одноразовый |
| Ротация | Нет | Да, при каждом использовании |

### 14.3.4. Правила

- **Пароль:** минимум 8 символов, хотя бы 1 буква, 1 цифра, 1 спецсимвол.
- **Хранение пароля:** bcrypt (cost 12).
- **MFA:** обязательна для администраторов, опциональна для клиентов.
- **Блокировка:** после 5 неудачных попыток — блок на 15 минут.
- **Защита от утечек:** проверка пароля по базе HaveIBeenPwned.

### 14.3.5. Аутентификация сервис-сервис

**mTLS (mutual TLS)** между микросервисами.

- Каждый сервис имеет клиентский сертификат.
- Проверка сертификата обеими сторонами.
- Ротация сертификатов: раз в 90 дней.

## 14.4. Авторизация

### 14.4.1. Модель RBAC

| Роль | Права |
|------|-------|
| **USER** | Своя корзина, свои заказы |
| **OPERATOR** | Просмотр всех заказов, разбор инцидентов |
| **ADMIN** | Полный доступ |
| **SERVICE** | Внутренние вызовы между сервисами |

### 14.4.2. Матрица доступа

| Ресурс | USER | OPERATOR | ADMIN | SERVICE |
|--------|------|----------|-------|---------|
| `GET /cart` | Своя | — | Да | Да |
| `POST /checkout/confirm` | Свой | — | Да | Да |
| `GET /orders/{id}` | Свой | Любой | Любой | Да |
| `POST /orders/{id}/cancel` | Свой | Любой | Любой | Да |
| `POST /payments/webhook` | — | — | — | Только Payment |
| `GET /admin/*` | — | Частично | Да | — |

### 14.4.3. Проверка ownership (IDOR)

**Каждый запрос проверяет, что объект принадлежит пользователю:**

```sql
SELECT * FROM orders 
WHERE id = :order_id 
  AND user_id = :current_user_id;
```

Если запись не найдена — `404 Not Found` (не `403`, чтобы не раскрывать существование объекта).

## 14.5. Защита данных

### 14.5.1. Шифрование в транзите

| Канал | Протокол |
|-------|----------|
| Клиент → API Gateway | TLS 1.3 |
| API Gateway → Сервисы | mTLS |
| Сервисы → БД | TLS |
| Сервисы → Kafka | TLS + SASL |
| Сервисы → Внешние API | TLS 1.3 |

**TLS-настройки:**
- Только TLS 1.3 (TLS 1.2 — для legacy).
- Cipher suites: TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256.
- HSTS: `max-age=31536000; includeSubDomains; preload`.
- Certificate pinning для мобильных приложений.

### 14.5.2. Шифрование в покое

| Данные | Шифрование |
|--------|-----------|
| БД | AES-256 (at-rest) |
| Бэкапы | AES-256 |
| Секреты | HashiCorp Vault |
| Логи | AES-256 |
| Файлы | AES-256 |

### 14.5.3. Токенизация платёжных данных

**Платёжные данные НЕ хранятся на наших серверах.**

Схема:
1. Клиент вводит карту в iframe Payment Gateway.
2. Payment Gateway возвращает токен.
3. Мы храним только токен.
4. При оплате передаём токен обратно.

**Что хранится:**
- `payment_method`: CARD, SBP, WALLET.
- `external_id`: токен от шлюза.
- Последние 4 цифры карты (для отображения).

**Что НЕ хранится:**
- PAN (номер карты).
- CVV.
- Срок действия.

### 14.5.4. Маскирование в логах

| Данные | Маскирование |
|--------|--------------|
| Email | `u***@example.com` |
| Телефон | `+7***1234567` |
| Карта | `**** **** **** 1234` |
| Токен | `eyJ***...` |

**Правило:** в логах только ID, не полные ПДн.

## 14.6. Соответствие PCI DSS

### 14.6.1. Уровень

**SAQ A** — минимальный уровень, потому что:
- Платёжные данные не хранятся.
- Все платежи через iframe Payment Gateway.
- Только redirect на страницу шлюза.

### 14.6.2. Требования

| Требование | Как выполняем |
|------------|---------------|
| 1. Firewall | WAF + Security Groups |
| 2. Не использовать дефолтные пароли | Уникальные пароли, ротация |
| 3. Защита хранимых данных | Токенизация, шифрование |
| 4. Шифрование в транзите | TLS 1.3 |
| 5. Антивирус | ClamAV на серверах |
| 6. Secure development | Code review, SAST |
| 7. Доступ по need-to-know | RBAC |
| 8. Идентификация пользователей | MFA для админов |
| 9. Физический доступ | Дата-центр с контролем |
| 10. Логирование | Централизованные логи |
| 11. Тестирование безопасности | Пентест раз в год |
| 12. Политики безопасности | Документация |

### 14.6.3. Аудит

- **Ежегодный** внешний аудит.
- **Ежеквартальный** внутренний скан.
- **ASV-скан** (Approved Scanning Vendor) раз в квартал.

## 14.8. Защита от атак (OWASP Top 10)

### 14.8.1. A01: Broken Access Control

**Митигация:**
- RBAC на каждом эндпоинте.
- Проверка ownership.
- Принцип least privilege.

### 14.8.2. A02: Cryptographic Failures

**Митигация:**
- TLS 1.3 везде.
- AES-256 at-rest.
- Токенизация платёжных данных.
- Хеширование паролей (bcrypt).

### 14.8.3. A03: Injection

**Митигация:**
- Prepared statements / ORM.
- Валидация входных данных.
- Экранирование вывода.
- SAST-сканирование.

### 14.8.4. A04: Insecure Design

**Митигация:**
- Threat modeling на этапе проектирования.
- Ревью архитектуры.
- Пентесты.

### 14.8.5. A05: Security Misconfiguration

**Митигация:**
- Infrastructure as Code (Terraform).
- Автоматическая проверка конфигов.
- Отключение debug в проде.
- Скрытие версий.

### 14.8.6. A06: Vulnerable Components

**Митигация:**
- Dependabot для обновлений.
- Snyk для сканирования.
- Регулярное обновление зависимостей.

### 14.8.7. A07: Authentication Failures

**Митигация:**
- MFA.
- Блокировка после 5 попыток.
- Проверка пароля по HaveIBeenPwned.
- Короткий TTL токенов.

### 14.8.8. A08: Data Integrity Failures

**Митигация:**
- Подпись webhook (HMAC).
- Проверка целостности событий.
- SRI для CDN-ресурсов.

### 14.8.9. A09: Logging Failures

**Митигация:**
- Централизованные логи.
- Алерты на подозрительные действия.
- Retention 30 дней – 1 год.

### 14.8.10. A10: SSRF

**Митигация:**
- Whitelist URL для внешних вызовов.
- Запрет внутренних IP.
- Валидация URL.

## 14.9. Rate Limiting и антифрод

### 14.9.1. Rate limiting

| Тип запроса | Лимит | Окно |
|-------------|-------|------|
| GET | 100 RPS | 1 минута |
| POST | 20 RPS | 1 минута |
| POST `/checkout/confirm` | 5 RPS | 1 минута |
| POST `/auth/login` | 5 попыток | 15 минут |
| Webhook | 1000 RPS | 1 минута |

**Реализация:** Redis + Token Bucket.

**Ответ при превышении:** `429 Too Many Requests` + `Retry-After`.

### 14.9.2. Антифрод

| Правило | Действие |
|---------|----------|
| Сумма заказа > 500 000 ₽ | Дополнительная проверка |
| 10+ заказов с одной карты за час | Блокировка карты |
| Заказ с разных IP за минуту | CAPTCHA |
| Множественные отмены | Ручная проверка |
| Смена адреса доставки после оплаты | Отмена заказа |

**Интеграция:** внешний антифрод-сервис (например, Sift, Forter).

## 14.10. Аудит и логирование

### 14.10.1. Что логируем

| Событие | Уровень | Retention |
|---------|---------|-----------|
| Вход в систему | INFO | 1 год |
| Неудачный вход | WARN | 1 год |
| Изменение пароля | INFO | 1 год |
| Создание заказа | INFO | 5 лет |
| Отмена заказа | INFO | 5 лет |
| Изменение статуса | INFO | 5 лет |
| Доступ к админке | INFO | 1 год |
| Изменение прав | WARN | 5 лет |
| Подозрительные действия | ERROR | 5 лет |

### 14.10.2. Формат audit-лога

```json
{
  "timestamp": "2026-10-16T12:00:00Z",
  "event": "ORDER_CANCELLED",
  "actor": {
    "user_id": "u1u2u3u4",
    "role": "USER",
    "ip": "192.168.1.1",
    "user_agent": "Mozilla/5.0..."
  },
  "target": {
    "type": "order",
    "id": "o1o2o3o4"
  },
  "result": "SUCCESS",
  "reason": "CUSTOMER_REQUEST",
  "correlation_id": "c1c2c3c4"
}
```

### 14.10.3. Неизменяемость

- Audit-логи пишутся в **append-only** хранилище.
- Хеширование записей (blockchain-like).
- Хранение в отдельной БД с ограниченным доступом.

## 14.11. Управление секретами

### 14.11.1. HashiCorp Vault

- Все секреты в Vault.
- Динамическая генерация credentials для БД.
- TTL секретов: 24 часа.
- Ротация: автоматическая.

### 14.11.2. Что хранится в Vault

| Секрет | TTL | Ротация |
|--------|-----|---------|
| Пароли БД | 24 часа | Автоматически |
| API-ключи | 30 дней | Вручную |
| JWT signing keys | 90 дней | Автоматически |
| TLS-сертификаты | 90 дней | Автоматически |
| Kafka credentials | 30 дней | Автоматически |
| Payment Gateway keys | 180 дней | Вручную |

### 14.11.3. Правила

- **Никаких секретов в коде.**
- **Никаких секретов в Git.**
- **Никаких секретов в логах.**
- **Секреты только через Vault.**
- **Аудит доступа к секретам.**
