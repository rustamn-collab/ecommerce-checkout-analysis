# 5. Use Cases

## 5.1. Назначение документа

Раздел описывает сценарии использования системы оформления заказа с точки зрения клиента и внешних систем. Каждый Use Case содержит:
- Актора
- Предусловие (Precondition)
- Постусловие (Postcondition)
- Основной поток (Main Flow)
- Альтернативные потоки (Alternative Flows)
- Исключительные ситуации (Exception Flows)
- Бизнес-правила (Business Rules)
- Критерии приёмки (Acceptance Criteria)
- Трассировку на FR, API и Sequence-диаграмму

**Акторы:**
- **Клиент** — пользователь мобильного приложения или сайта.
- **Frontend** — мобильное приложение / веб-сайт.
- **Cart Service** — микросервис корзины.
- **Checkout Service** — микросервис оформления заказа.
- **Logistics Service** — микросервис расчёта доставки.
- **Payment Gateway** — внешний платёжный шлюз.
- **ERP System** — система учёта остатков и заказов.
- **Notification Service** — сервис уведомлений.

## 5.2. UC-01: Оформление заказа с курьерской доставкой и онлайн-оплатой

**ID:** UC-01
**Название:** Оформление заказа с курьерской доставкой и онлайн-оплатой
**Актор:** Клиент
**Уровень:** Пользовательская цель (User Goal)
**Приоритет:** Must
**Трассировка:** FR-01..FR-48, sequence-diagram, api-contracts

### 5.2.1. Краткое описание

Клиент добавляет товары в корзину, выбирает адрес и слот доставки, оплачивает заказ онлайн и получает подтверждение. Система резервирует товар, создаёт заказ в ERP, публикует события в Kafka и отправляет уведомления.

### 5.2.2. Предусловие (Precondition)

- Клиент авторизован в системе.
- В корзине есть хотя бы один товар.
- Товар есть в наличии на складе (проверяется при расчёте корзины).
- Адрес доставки входит в зону обслуживания.
- Payment Gateway доступен.

### 5.2.3. Постусловие (Postcondition)

**Успешное завершение:**
- Заказ создан в ERP с уникальным номером.
- Товар зарезервирован и впоследствии отгружен.
- Оплата проведена.
- Клиент получил push/SMS-уведомление.
- Событие `order.confirmed` опубликовано в Kafka.
- Заказ передан в курьерскую службу.

**Неуспешное завершение:**
- Заказ не создан или отменён.
- Резерв товара снят.
- Возврат средств инициирован (если оплата прошла).

### 5.2.4. Основной поток (Main Flow)

| Шаг | Актор | Действие |
|-----|-------|----------|
| 1 | Клиент | Открывает корзину в мобильном приложении или на сайте |
| 2 | Frontend | Отправляет `GET /api/v1/cart` в API Gateway |
| 3 | Cart Service | Запрашивает у ERP актуальные остатки и цены |
| 4 | ERP | Возвращает данные о наличии и ценах |
| 5 | Cart Service | Запрашивает у Logistics Service варианты доставки |
| 6 | Logistics Service | Возвращает доступные слоты и стоимость |
| 7 | Cart Service | Формирует ответ с итоговой суммой |
| 8 | Frontend | Отображает корзину клиенту |
| 9 | Клиент | Выбирает адрес доставки и слот |
| 10 | Клиент | Выбирает способ оплаты |
| 11 | Клиент | Нажимает «Оформить заказ» |
| 12 | Frontend | Отправляет `POST /api/v1/checkout/confirm` |
| 13 | Checkout Service | Создаёт черновик заказа (статус `DRAFT`) |
| 14 | Checkout Service | Резервирует товар на 15 минут |
| 15 | Checkout Service | Инициирует платёж в Payment Gateway |
| 16 | Payment Gateway | Возвращает ссылку на платёжную форму |
| 17 | Frontend | Перенаправляет клиента на оплату |
| 18 | Клиент | Вводит платёжные данные |
| 19 | Payment Gateway | Отправляет webhook `payment.success` |
| 20 | Checkout Service | Проверяет подпись webhook |
| 21 | Checkout Service | Меняет статус заказа на `PAID` |
| 22 | Checkout Service | Подтверждает заказ в ERP |
| 23 | ERP | Присваивает номер заказа, подтверждает резерв |
| 24 | Checkout Service | Публикует `order.confirmed` в Kafka |
| 25 | Kafka | Доставляет событие в Notification Service и Logistics Service |
| 26 | Notification Service | Отправляет клиенту push/SMS |
| 27 | Logistics Service | Передаёт заказ в курьерскую службу |
| 28 | Frontend | Показывает экран «Заказ успешно оформлен» |

### 5.2.5. Альтернативные потоки (Alternative Flows)

#### AF-01: Товара нет на складе (UC-01.A)

**Точка ветвления:** шаг 3 основного потока.

| Шаг | Актор | Действие |
|-----|-------|----------|
| 3a | ERP | Возвращает `out of stock` для одного или нескольких товаров |
| 3b | Cart Service | Помечает товар как «нет в наличии» |
| 3c | Cart Service | Возвращает `409 Conflict` с деталями |
| 3d | Frontend | Отображает сообщение «Товар закончился» |
| 3e | Клиент | Выбирает: удалить товар или сохранить корзину |
| 3f | Клиент | Если удаляет — корзина пересчитывается, поток возвращается к шагу 3 |
| 3g | Клиент | Если сохраняет — чекаут невозможен до появления товара |

**Бизнес-правило:** BR-01 (товар без остатка не может быть оформлен, но остаётся в корзине).

**Трассировка:** FR-06, FR-43.

#### AF-02: Альтернативный склад (UC-01.A.1)

**Точка ветвления:** шаг 3a.

| Шаг | Актор | Действие |
|-----|-------|----------|
| 3a-1 | ERP | Возвращает `out of stock` на основном складе |
| 3a-2 | ERP | Возвращает альтернативные склады с наличием |
| 3a-3 | Cart Service | Предлагает клиенту альтернативу |
| 3a-4 | Клиент | Соглашается на доставку с другого склада |
| 3a-5 | Cart Service | Пересчитывает доставку с учётом нового склада |
| 3a-6 | Cart Service | Возвращается к шагу 7 основного потока |

**Бизнес-правило:** BR-07 (доставка с разных складов = отдельные отправления).

**Трассировка:** FR-07, FR-15.

#### AF-03: Слот доставки недоступен (UC-01.B.1)

**Точка ветвления:** шаг 12 основного потока.

| Шаг | Актор | Действие |
|-----|-------|----------|
| 12a | Checkout Service | Обнаруживает, что выбранный слот занят |
| 12b | Checkout Service | Возвращает `409 Conflict` с альтернативными слотами |
| 12c | Frontend | Показывает клиенту список доступных слотов |
| 12d | Клиент | Выбирает новый слот |
| 12e | Frontend | Повторно отправляет `POST /checkout/confirm` |
| 12f | Поток возвращается к шагу 13 основного потока |

**Трассировка:** FR-13, FR-44.

#### AF-04: Оплата не прошла (UC-01.B)

**Точка ветвления:** шаг 19 основного потока.

| Шаг | Актор | Действие |
|-----|-------|----------|
| 19a | Payment Gateway | Отправляет webhook `payment.failed` |
| 19b | Checkout Service | Меняет статус заказа на `PAYMENT_FAILED` |
| 19c | Checkout Service | Публикует `payment.failed` в Kafka |
| 19d | Frontend | Показывает сообщение «Оплата не прошла» |
| 19e | Клиент | Выбирает один из вариантов ниже |

**Вложенные сценарии:**

**AF-04.1: Клиент повторяет оплату**
- Клиент нажимает «Попробовать снова».
- Checkout Service создаёт новый платёж.
- Поток возвращается к шагу 16 основного потока.

**AF-04.2: Клиент отменяет заказ**
- Клиент нажимает «Отменить заказ».
- Checkout Service снимает резерв товара.
- Публикует `order.cancelled` в Kafka.
- Клиент получает уведомление «Заказ отменён».

**AF-04.3: Таймаут 15 минут**
- Если клиент не предпринял действий — резерв снимается автоматически.
- Публикуется `order.expired` в Kafka.
- Заказ помечается как `EXPIRED`.

**Трассировка:** FR-26, FR-30, FR-36.

#### AF-05: Отмена заказа после успешной оплаты (UC-01.C)

**Точка ветвления:** после шага 26 основного потока.

| Шаг | Актор | Действие |
|-----|-------|----------|
| 26a | Клиент | Нажимает «Отменить заказ» |
| 26b | Frontend | Отправляет `POST /checkout/cancel` |
| 26c | Checkout Service | Проверяет статус заказа (не передан ли курьеру) |
| 26d | Checkout Service | Инициирует возврат через Payment Gateway |
| 26e | Payment Gateway | Подтверждает возврат |
| 26f | Checkout Service | Снимает резерв в ERP |
| 26g | Checkout Service | Публикует `order.cancelled` в Kafka |
| 26h | Notification Service | Уведомляет клиента о возврате (3–5 дней) |
| 26i | Frontend | Показывает экран «Заказ отменён» |

**Бизнес-правило:** BR-13 (отмена невозможна после IN_TRANSIT).

**Трассировка:** FR-31..FR-34.

### 5.2.6. Исключительные ситуации (Exception Flows)

#### EF-01: ERP недоступна

- Checkout Service получает таймаут от ERP.
- Возвращает клиенту `503 Service Unavailable`.
- Логирует инцидент.
- Frontend показывает «Сервис временно недоступен, попробуйте позже».
- Circuit Breaker размыкается на 30 секунд.

**Трассировка:** FR-45, NFR-11.

#### EF-02: Payment Gateway недоступен

- Checkout Service получает таймаут от Payment Gateway.
- Пробует retry с exponential backoff (3 попытки).
- Если все попытки неудачны — заказ помечается `PAYMENT_FAILED`.
- Клиент получает уведомление.

**Трассировка:** FR-46.

#### EF-03: Дублирование webhook от Payment Gateway

- Checkout Service получает webhook с уже обработанным `payment_id`.
- Проверяет идемпотентность по `payment_id`.
- Не создаёт дубль заказа.
- Возвращает `200 OK` шлюзу.

**Бизнес-правило:** BR-11 (идемпотентность).

**Трассировка:** FR-29.

#### EF-04: Зависшее событие в Kafka

- Событие не обрабатывается более 1 часа.
- Автоматически перемещается в DLQ.
- Алерт в PagerDuty.
- Дежурный инженер разбирает инцидент.

**Трассировка:** FR-48.

#### EF-05: Клиент дважды нажал «Оплатить»

- Frontend отправляет два одинаковых запроса с одинаковым `Idempotency-Key`.
- Checkout Service обрабатывает только первый.
- Второй запрос возвращает тот же результат без создания нового заказа.

**Трассировка:** FR-29.

### 5.2.7. Бизнес-правила (Business Rules)

| ID | Правило |
|----|---------|
| BR-01 | Товар без остатка не может быть оформлен, но остаётся в корзине |
| BR-02 | Цена фиксируется на момент оформления заказа |
| BR-03 | Максимальная сумма корзины — 500 000 ₽ |
| BR-04 | Максимум 50 позиций в корзине |
| BR-05 | Бесплатная доставка при сумме ≥ 10 000 ₽ |
| BR-06 | Крупногабарит — отдельный транспорт с доплатой |
| BR-07 | Товары с разных складов = отдельные отправления |
| BR-08 | Слоты доступны на 14 дней вперёд |
| BR-09 | Заказ без слота доставки создать нельзя |
| BR-10 | Резерв действует 15 минут |
| BR-11 | Идемпотентность через Idempotency-Key |
| BR-12 | Неоплата в течение 15 минут → EXPIRED |
| BR-13 | Отмена возможна только до IN_TRANSIT |
| BR-14 | Возврат средств — 3–5 рабочих дней |
| BR-15 | Для неоплаченного заказа возврат не требуется |

### 5.2.8. Критерии приёмки (Acceptance Criteria)

| ID | Критерий | Проверка |
|----|----------|----------|
| AC-01 | Клиент может оформить заказ с доставкой и онлайн-оплатой | E2E-тест |
| AC-02 | При отсутствии товара показывается сообщение | E2E-тест |
| AC-03 | Резерв товара снимается через 15 минут при неоплате | Автотест |
| AC-04 | Повторное нажатие «Оплатить» не создаёт дубль | Автотест |
| AC-05 | При оплате не прошла — клиент может повторить или отменить | E2E-тест |
| AC-06 | Отмена оплаченного заказа инициирует возврат | E2E-тест |
| AC-07 | Все события публикуются в Kafka | Логи Kafka |
| AC-08 | Уведомления приходят на каждом этапе | Push/SMS-тест |
| AC-09 | p95 расчёта корзины ≤ 1,5 сек | Нагрузочный тест |
| AC-10 | p95 подтверждения заказа ≤ 2 сек | Нагрузочный тест |

## 5.3. UC-02: Администратор проверяет зависшие заказы

**ID:** UC-02
**Название:** Проверка зависших заказов оператором
**Актор:** Оператор клиентского сервиса
**Приоритет:** Should
**Трассировка:** FR-48

### 5.3.1. Краткое описание

Оператор просматривает заказы в статусах `PAYMENT_FAILED`, `EXPIRED`, `CANCELLED` и разбирает инциденты интеграции, если они попали в DLQ.

### 5.3.2. Предусловие

- Оператор авторизован в админ-панели.
- Есть зависшие заказы или сообщения в DLQ.

### 5.3.3. Основной поток

| Шаг | Актор | Действие |
|-----|-------|----------|
| 1 | Оператор | Открывает дашборд «Зависшие заказы» |
| 2 | Система | Показывает список заказов с фильтрами |
| 3 | Оператор | Выбирает заказ для разбора |
| 4 | Система | Показывает детали: статус, историю, ошибки |
| 5 | Оператор | Принимает решение: перевести в `CONFIRMED`, `CANCELLED` или `REFUNDED` |
| 6 | Система | Обновляет статус, публикует событие в Kafka |
| 7 | Система | Логирует действие оператора |

### 5.3.4. Постусловие

Заказ приведён к финальному статусу, событие опубликовано, действие залогировано.

### 5.3.5. Бизнес-правила

- **BR-21:** Оператор не может изменить оплаченный заказ без согласования с финансами.
- **BR-22:** Все действия оператора аудируются.

### 5.3.6. Критерии приёмки

| ID | Критерий |
|----|----------|
| AC-11 | Оператор видит список зависших заказов |
| AC-12 | Оператор может изменить статус заказа |
| AC-13 | Действие оператора логируется |
| AC-14 | Все изменения публикуются в Kafka |

## 5.4. UC-03: Клиент отслеживает статус заказа

**ID:** UC-03
**Название:** Отслеживание статуса заказа
**Актор:** Клиент
**Приоритет:** Should
**Трассировка:** FR-37..FR-42

### 5.4.1. Краткое описание

Клиент просматривает историю заказов и текущий статус активного заказа.

### 5.4.2. Предусловие

- Клиент авторизован.
- У клиента есть хотя бы один заказ.

### 5.4.3. Основной поток

| Шаг | Актор | Действие |
|-----|-------|----------|
| 1 | Клиент | Открывает раздел «Мои заказы» |
| 2 | Frontend | Отправляет `GET /api/v1/orders` |
| 3 | Order Service | Возвращает список заказов с пагинацией |
| 4 | Клиент | Выбирает конкретный заказ |
| 5 | Frontend | Отправляет `GET /api/v1/orders/{id}` |
| 6 | Order Service | Возвращает детали заказа и статус |
| 7 | Frontend | Отображает статус, состав заказа, трек-номер |

### 5.4.4. Постусловие

Клиент видит актуальный статус заказа.

### 5.4.5. Критерии приёмки

| ID | Критерий |
|----|----------|
| AC-15 | Клиент видит список своих заказов |
| AC-16 | Клиент видит детали и статус заказа |
| AC-17 | Трек-номер отображается, если доступен |
