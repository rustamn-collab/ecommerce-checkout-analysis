# 4. Нефункциональные требования (NFR)

## 4.1. Назначение документа

Нефункциональные требования описывают, **как** система должна работать: с какой скоростью, надёжностью, безопасностью и удобством сопровождения. Они не менее важны, чем функциональные, потому что именно NFR определяют, выдержит ли чекаут пиковые распродажи и останется ли он отказоустойчивым.

## 4.3. Доступность и надёжность

| ID | Требование | Значение |
|----|------------|----------|
| NFR-11 | SLA чекаута | 99,95% |
| NFR-12 | SLA API Gateway | 99,99% |
| NFR-13 | SLA Payment Gateway (внешний) | 99,9% |
| NFR-14 | SLA ERP (внутренний) | 99,9% |
| NFR-15 | RTO (Recovery Time Objective) | ≤ 15 минут |
| NFR-16 | RPO (Recovery Point Objective) | ≤ 5 минут |
| NFR-17 | Максимальное время недоступности в месяц | ≤ 22 минуты |
| NFR-18 | Допустимая потеря событий Kafka | 0 (at-least-once) |
| NFR-19 | Допустимое количество дублей заказов | 0 |
| NFR-20 | MTTR (Mean Time To Recovery) | ≤ 15 минут |

### Обоснование SLA

- **99,95%** — стандарт для высоконагруженных e-commerce систем.
- **RTO 15 минут** — критично для чекаута: каждый час простоя = потеря выручки.
- **RPO 5 минут** — допустимая потеря данных при аварии.
- **MTTR 15 минут** — команда должна восстанавливать сервис за это время.

## 4.4. Масштабируемость

| ID | Требование | Значение |
|----|------------|----------|
| NFR-21 | Горизонтальное масштабирование сервисов | Да |
| NFR-22 | Автомасштабирование при пиках | Да (HPA) |
| NFR-23 | Партиционирование Kafka | ≥ 6 партиций на топик |
| NFR-24 | Шардирование БД | При росте > 10 млн заказов |
| NFR-25 | Кэширование (Redis) | Для остатков и цен |
| NFR-26 | CDN для статики | Да |
| NFR-27 | Read-replicas PostgreSQL | ≥ 2 реплики |
| NFR-28 | Connection pool | ≥ 100 соединений на сервис |

### Стратегия масштабирования

- **Сервисы:** stateless, масштабируются горизонтально через Kubernetes.
- **БД:** вертикальное масштабирование до 10 млн заказов, затем шардирование.
- **Kafka:** увеличение партиций при росте нагрузки.
- **Кэш:** Redis для горячих данных (остатки, цены).

## 4.5. Безопасность

| ID | Требование | Значение |
|----|------------|----------|
| NFR-29 | Аутентификация | JWT / OAuth 2.0 |
| NFR-30 | Шифрование трафика | TLS 1.3 |
| NFR-31 | Соответствие PCI DSS | Да (для платежей) |
| NFR-32 | Хранение платёжных данных | Не хранить (токенизация) |
| NFR-33 | Защита от CSRF | Да |
| NFR-34 | Защита от XSS | Да |
| NFR-35 | Rate limiting | 100 RPS на пользователя |
| NFR-36 | DDoS-защита | Cloudflare / WAF |
| NFR-37 | Аудит действий пользователя | 90 дней |
| NFR-38 | Хранение персональных данных | 152-ФЗ, серверы в РФ |

### Требования PCI DSS

- Платёжные данные **не хранятся** на наших серверах.
- Используется **токенизация** через Payment Gateway.
- Все запросы к шлюзу — по TLS 1.3.
- Логи не содержат PAN-номеров карт.
