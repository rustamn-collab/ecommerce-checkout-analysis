# 3. Функциональные требования (FR)

## 3.1. Назначение документа

Документ описывает функциональные требования к системе оформления заказа (чекаут) в e-commerce. Каждое требование имеет уникальный идентификатор (FR-XX), приоритет (Must / Should / Could) и трассировку на Use Cases и API-методы.

**Приоритеты:**
- **Must** — без этого релиз невозможен.
- **Should** — важно, но можно отложить на следующий релиз.
- **Could** — желательно, реализуется при наличии ресурсов.

## 3.2. Блок 1: Управление корзиной

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-01 | Клиент может добавить товар в корзину из карточки товара или каталога | Must |
| FR-02 | Клиент может изменить количество товара в корзине | Must |
| FR-03 | Клиент может удалить товар из корзины | Must |
| FR-04 | Система проверяет актуальные остатки в ERP при открытии корзины | Must |
| FR-05 | Система проверяет актуальные цены в ERP при открытии корзины | Must |
| FR-06 | Система помечает товары, которых нет в наличии, как «нет в наличии» | Must |
| FR-07 | Система предлагает альтернативные склады, если товара нет на основном | Should |
| FR-08 | Корзина сохраняется между сессиями (для авторизованного клиента) | Should |
| FR-09 | Корзина сохраняется при смене устройства (для авторизованного клиента) | Could |
| FR-10 | Система ограничивает максимальное количество одного товара в корзине (не более 99 шт.) | Must |

### Бизнес-правила блока «Корзина»

- **BR-01:** Если товара нет на складе, он не может быть оформлен, но остаётся в корзине.
- **BR-02:** Цена фиксируется на момент оформления заказа, а не на момент добавления в корзину.
- **BR-03:** Максимальная сумма корзины — 500 000 ₽ (антифрод-ограничение).
- **BR-04:** Максимальное количество позиций в корзине — 50.

## 3.3. Блок 2: Расчёт доставки

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-11 | Система рассчитывает стоимость доставки на основе адреса | Must |
| FR-12 | Система рассчитывает стоимость доставки на основе габаритов и веса | Must |
| FR-13 | Система предлагает доступные интервалы доставки (слоты) | Must |
| FR-14 | Система учитывает загрузку складов и курьерских служб | Should |
| FR-15 | Система поддерживает доставку с разных складов (сплитование) | Must |
| FR-16 | Система отображает ориентировочную дату доставки | Should |
| FR-17 | Система рассчитывает стоимость доставки для крупногабаритных товаров отдельно | Must |
| FR-18 | Система предлагает бесплатную доставку при сумме заказа выше порога | Should |

### Бизнес-правила блока «Доставка»

- **BR-05:** Бесплатная доставка при сумме заказа ≥ 10 000 ₽ (кроме крупногабарита).
- **BR-06:** Крупногабаритные товары доставляются отдельным транспортом с доплатой.
- **BR-07:** Если товары на разных складах — доставка рассчитывается как несколько отправлений.
- **BR-08:** Слоты доставки доступны на 14 дней вперёд.

## 3.4. Блок 3: Оформление заказа (Чекаут)

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-19 | Клиент может указать адрес доставки | Must |
| FR-20 | Клиент может выбрать слот доставки | Must |
| FR-21 | Клиент может выбрать способ оплаты (карта, СБП, кошелёк) | Must |
| FR-22 | Система резервирует товар на 15 минут при переходе к оплате | Must |
| FR-23 | Система создаёт черновик заказа | Must |
| FR-24 | Система инициирует оплату через Payment Gateway | Must |
| FR-25 | Система обрабатывает webhook об успешной оплате | Must |
| FR-26 | Система обрабатывает webhook о неуспешной оплате | Must |
| FR-27 | Система подтверждает заказ в ERP после успешной оплаты | Must |
| FR-28 | Система публикует событие `order.confirmed` в Kafka | Must |
| FR-29 | Система поддерживает идемпотентность при повторном нажатии «Оплатить» | Must |
| FR-30 | Система автоматически снимает резерв через 15 минут при неоплате | Must |

### Бизнес-правила блока «Чекаут»

- **BR-09:** Заказ не может быть создан без выбора слота доставки.
- **BR-10:** Резерв товара действует 15 минут с момента создания черновика заказа.
- **BR-11:** Повторное нажатие «Оплатить» не создаёт дубль заказа (Idempotency-Key).
- **BR-12:** Если оплата не поступила в течение 15 минут — заказ переходит в статус EXPIRED.

## 3.5. Блок 4: Отмена и возврат

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-31 | Клиент может отменить заказ до передачи курьеру | Must |
| FR-32 | Система инициирует возврат средств при отмене оплаченного заказа | Must |
| FR-33 | Система снимает резерв товара при отмене | Must |
| FR-34 | Система уведомляет клиента о возврате средств | Must |
| FR-35 | Система блокирует отмену заказа, если он передан курьеру | Must |
| FR-36 | Система публикует событие `order.cancelled` в Kafka | Must |

### Бизнес-правила блока «Отмена»

- **BR-13:** Отмена возможна только до статуса IN_TRANSIT.
- **BR-14:** Возврат средств — 3–5 рабочих дней (зависит от банка).
- **BR-15:** При отмене неоплаченного заказа возврат не требуется.

## 3.6. Блок 5: Уведомления

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-37 | Система отправляет push/SMS при создании заказа | Must |
| FR-38 | Система отправляет push/SMS при успешной оплате | Must |
| FR-39 | Система отправляет push/SMS при сборке заказа | Should |
| FR-40 | Система отправляет push/SMS при передаче курьеру | Should |
| FR-41 | Система отправляет push/SMS при доставке | Should |
| FR-42 | Система отправляет email с чеком об оплате | Should |

### Бизнес-правила блока «Уведомления»

- **BR-16:** Уведомления отправляются только авторизованным клиентам.
- **BR-17:** Клиент может отключить маркетинговые уведомления, но не транзакционные.

## 3.7. Блок 6: Обработка ошибок

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-43 | Система возвращает 409 при отсутствии товара на складе | Must |
| FR-44 | Система возвращает 409 при недоступности слота доставки | Must |
| FR-45 | Система возвращает 503 при недоступности ERP | Must |
| FR-46 | Система возвращает 503 при недоступности Payment Gateway | Must |
| FR-47 | Система логирует все ошибки интеграций | Must |
| FR-48 | Система отправляет зависшие события в DLQ | Must |

### Бизнес-правила блока «Ошибки»

- **BR-18:** Все ошибки возвращаются в едином формате `{ error, message, details }`.
- **BR-19:** При недоступности внешней системы — retry с exponential backoff.
- **BR-20:** Зависшие события старше 1 часа уходят в DLQ.
